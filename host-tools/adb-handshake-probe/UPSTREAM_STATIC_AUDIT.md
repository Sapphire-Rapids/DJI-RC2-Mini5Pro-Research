# Dr-Muh/dji-adb upstream static audit

Audit time: 2026-08-28 (Asia/Shanghai)
Scope: static review plus an isolated Python 3.14 import/key-generation smoke test. No USB device was enumerated, opened, claimed or written by this audit. The upstream clone was left clean.

## Verdict

The repository is useful as a compact statement of one known-working RC2 authentication profile, but `djiadb.py` is not suitable as the first evidence-producing live probe on RC2 v07.00.0100.

- Its defining behavior is real and unambiguous: send `CNXN`, accept only `AUTH/TOKEN`, skip `AUTH/SIGNATURE`, then send a NUL-terminated `AUTH/RSAPUBLICKEY` and expect `CNXN`.
- It hard-codes the old observed USB interface and three pre-auth compatibility variables; the README says only firmware `v02.00.0300` was tested.
- It does not validate incoming ADB magic, checksum, payload length or stream identity, does not accumulate short USB reads, and does not classify/log timeout vs stall vs reset.
- It changes host/device state before a shell is entered: it may create an ADB key pair, exclusively claims interface 2, clears both endpoint halt states, sends ADB traffic, and can cause the RC2 to persist an accepted public key.
- It does **not** automatically run a shell command, reboot, flash, unlock, install an APK or modify DJI configuration. Arbitrary commands are sent only after a successful handshake and explicit terminal input.

Therefore the safe order is: run `listadb.py` only to confirm the live descriptor, then use a separate instrumented **handshake-only** client that preserves the upstream profile but stops at `CNXN` and logs every packet/USB exception. Do not enter the upstream interactive shell until the handshake is understood.

## Exact USB profile

`djiadb.py` hard-codes the following values at [lines 18-24](https://github.com/Dr-Muh/dji-adb/blob/027c7815568c89e55fff22bfeede9dd294404660/djiadb.py#L18-L24):

| Field | Value |
|---|---:|
| VID:PID | `2ca3:1021` |
| Interface | `2` |
| Expected class/subclass/protocol | `0xff / 0x42 / 0x01` (comment/README only) |
| Bulk OUT | `0x03` |
| Bulk IN | `0x84` |
| Per-transfer timeout | `15000 ms` |

The expected descriptor is documented in `README.md` lines 14-33, but the only declared tested firmware is `v02.00.0300` at lines 95-97. `djiadb.py` does not inspect or validate the actual interface class, endpoint type, maximum packet size, active configuration or alternate setting before claiming interface 2.

`listadb.py` is descriptor-oriented and does not claim an interface or send ADB bulk packets. Its exact behavior is:

- line 3 assigns `VENDOR_ID = None`, but line 4 immediately overwrites it with `0x2ca3`; the claimed “scan all” path is unreachable without editing the file;
- lines 6-9 enumerate every currently visible DJI-vendor USB device, not just PID `0x1021`;
- lines 11-18 request manufacturer/product strings. In `libusb1`, those helpers temporarily open the device and perform synchronous string-descriptor control reads; this is more than passive registry inspection, although it does not claim an interface;
- lines 20-28 print every configuration/interface/endpoint already exposed by libusb;
- it does not print or select by serial number, despite the README's historical sample containing `_SN:`.

`djiadb.py` uses `USBContext.getByVendorIDAndProductID`, which returns the **first** matching device. It has no bus/port/serial disambiguation if two `2ca3:1021` devices are present.

## Exact ADB packet profile

Command integers are generated by little-endian decoding of the four ASCII command bytes at `djiadb.py` lines 26-31:

| Command | Integer | Wire bytes |
|---|---:|---|
| `CNXN` | `0x4e584e43` | `43 4e 58 4e` |
| `AUTH` | `0x48545541` | `41 55 54 48` |
| `OPEN` | `0x4e45504f` | `4f 50 45 4e` |
| `OKAY` | `0x59414b4f` | `4f 4b 41 59` |
| `WRTE` | `0x45545257` | `57 52 54 45` |
| `CLSE` | `0x45534c43` | `43 4c 53 45` |

AUTH subtypes are `TOKEN=1`, `SIGNATURE=2`, `RSAPUBLICKEY=3`. The fixed connection profile at lines 31-33 and 80-102 is:

```text
VERSION = 0x01000000
MAXDATA = 0x00040000  (262144)
banner  = "host::pydevice\0" (15 bytes)

Host -> CNXN(version=0x01000000, maxdata=0x00040000, banner)
RC2  -> CNXN
    success without authentication
or
RC2  -> AUTH(TOKEN)
Host -> AUTH(RSAPUBLICKEY, arg1=0, raw adbkey.pub bytes + final NUL)
RC2  -> CNXN
    success
```

There is no `AUTH/SIGNATURE` send call. The token bytes are not signed or otherwise used. `PythonRSASigner` is still constructed and parses the private key, but only `GetPublicKey()` is called.

The exact first packet produced by `pack()` is:

```text
payload ASCII: host::pydevice\0
payload hex:   686f73743a3a707964657669636500
payload len:   15
checksum:      0x0000058b
magic:         0xb1a7b1bc
header hex:    434e584e00000001000004000f0000008b050000bcb1a7b1
```

`pack()` uses the legacy ADB six-`uint32` little-endian header, byte-sum checksum and `command ^ 0xffffffff` magic (`djiadb.py` lines 41-47). `send()` writes the 24-byte header and payload as two independent bulk transfers (`lines 49-53`). It prints transfer counts but does not fail on a short write.

The public-key path preserves the contents of `~/.android/adbkey.pub` verbatim and only appends `\0` if the final byte is not already NUL (`lines 95-101`). It does not remove a trailing newline, so “newline before NUL” is an uncontrolled compatibility variable for an externally generated `.pub` file.

## Receive/parser weaknesses relevant to live diagnosis

`recv()` at `djiadb.py` lines 55-59 performs one 24-byte bulk read and one `data_len` bulk read. It does not:

- accumulate a short header or short payload;
- verify that the header read returned exactly 24 bytes before unpacking;
- validate `magic == command ^ 0xffffffff`;
- validate the payload checksum;
- cap `data_len` at `MAXDATA` or another defensive limit;
- report command/arg0/arg1/checksum/magic/payload contents;
- distinguish `USBErrorTimeout`, pipe/stall, no-device/reset or partial-transfer counts.

The handshake accepts only one packet at each receive point. A repeated token, delayed authorization sequence, `STLS`, or any other packet is an immediate failure (`lines 82-109`). A 15-second receive timeout escapes as an uncategorized exception/traceback. This cannot answer whether v07 stopped at `CNXN -> timeout`, `RSAPUBLICKEY -> timeout`, or a USB reset without a wrapper.

The shell parser has additional correctness limits (`lines 113-137`): it records but never uses `remote_id`, accepts `WRTE` without binding `arg0` to the opened stream, and ignores packets by `arg1` alone. These do not affect a handshake-only probe, but they are reasons not to use this loop as a general ADB client.

An isolated macOS arm64 Python `3.14.0` environment resolved and installed:

```text
adb_shell==0.4.4
cffi==2.1.1
cryptography==50.0.1
libusb1==3.4.0
pyasn1==0.6.4

```

In that exact environment, importing `djiadb.py`, importing `usb1`, generating a temporary key pair, and loading it through `PythonRSASigner.FromRSAKeyPath()` all passed. No USB enumeration occurred. This proves the currently resolved dependency set works for those narrow operations on Python 3.14; it does **not** prove the USB handshake or interactive shell.

Compatibility cautions:

- `adb-shell 0.4.4` does not formally declare Python 3.14 support.
- Its key generator uses private API `cryptography.hazmat.primitives.asymmetric.rsa._modinv`; the exact `cryptography==50.0.1` smoke test passed, but an unpinned future release can remove that symbol.
- The key generator opens the unencrypted private key with ordinary `open(..., 'wb')` and does not `chmod(0600)`. Under this host's default umask, the isolated test produced mode `0644`. A harness should refuse to generate a real key implicitly and should validate existing key/public-key presence and permissions.
- `ensure_signer()` checks only whether the private key exists. If it is absent, it creates `~/.android` and a new private/public pair; an orphan existing `.pub` is overwritten. If the private key exists but `.pub` is missing, loading fails before USB open.

## Runtime side effects and failure modes

### `python listadb.py`

Risk: low, read-oriented but not zero-I/O.

- opens DJI-vendor devices temporarily to read manufacturer/product USB strings;
- reads descriptors and prints them;
- does not claim/detach interfaces, clear halts, reset the device, send ADB bulk traffic, create keys or execute commands.

### `python djiadb.py` before authentication completes

Risk: moderate and observable.

1. May create `~/.android/adbkey` and `.pub` (`lines 35-39`).
2. Opens the first `2ca3:1021` match (`lines 61-66`).
3. Requests automatic kernel-driver detach, swallowing all errors (`lines 67-70`).
4. Exclusively claims interface 2 (`line 71`), so a stock ADB server or another client cannot use it concurrently.
5. Calls `clearHalt()` on OUT `0x03` and IN `0x84` (`lines 72-77`). This changes endpoint halt state; it is not a passive check. There is no explicit USB device reset call.
6. Sends the fixed `CNXN`; after `AUTH/TOKEN`, sends the public key. Acceptance can display an RSA prompt and can persist authorization state on RC2.

If `claimInterface()` itself fails, `open_device()` has no local cleanup block. The main `finally` is entered only after `open_device()` returns, so cleanup then relies on object finalization/process exit. On the normal returned path, `releaseInterface()` and handle `close()` run, but the `USBContext` is not explicitly closed.

### After authentication

The script prints `Root shell ready` without first executing `id` or otherwise proving UID 0 (`lines 139-145`). It then waits for explicit user input. Each nonempty line is embedded in `shell:<command>\0` and sent in an `OPEN` packet (`lines 145-151`, `113-117`). Therefore:

- no command is automatic;
- any typed command can be state-changing and runs with whatever privilege the device's adbd grants;
- the script contains no guardrails, allowlist, read-only mode, confirmation, audit log or output-size bound.

Static keyword review found no subprocess/host-shell invocation, TCP path, fastboot, bootloader unlock, Magisk, device reboot/reset, firmware write or APK-install implementation in the tracked Python files.

## Required live-test posture

1. Stop the stock ADB server before any claim attempt.
2. Run the unmodified `listadb.py` once and record the actual v07 descriptor. Do not infer v07 from README's v02 sample.
3. Use a separate, reviewed handshake-only harness with the exact upstream first profile:
   `VERSION=0x01000000`, `MAXDATA=0x00040000`, `host::pydevice\0`, split header/payload writes, direct NUL-terminated `RSAPUBLICKEY` after `AUTH/TOKEN`.
4. The harness must validate and log every six-field header, bounded payload, short transfer and concrete libusb exception; it must stop after the first `CNXN` or terminal failure and never send `OPEN`.
5. Require the existing key pair; do not implicitly generate or alter it. Preserve whether the `.pub` payload contains newline before the required NUL.
6. Change only one compatibility variable per subsequent attempt. The upstream profile simultaneously differs from current stock ADB in version, `MAXDATA`, banner/features and bulk-write shape, so a success would not by itself identify which difference matters.
