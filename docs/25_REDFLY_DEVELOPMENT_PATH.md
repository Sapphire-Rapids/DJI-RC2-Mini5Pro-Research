## 参数编辑器值得借鉴的部分（C-481）

| 环节 | 当前代码实际做什么 | 对二开的意义 |
| --- | --- | --- |
| 参数发现 | E0 读取表规模，E1 逐项取得名称、类型、范围等元数据；`KnownGroups` 只负责分类 | 使用设备实际返回的元数据，避免把静态名称表当作支持证明 |
| 写入核对 | `verifiedWrite` 重新检查元数据及当前值，E3 写入后再发 E2 读值并比较 | 这是独立的值读取路径，比仅检查发送成功或 ACK 更有参考价值 |
| 通信 | `Wire extends DataBase`，经 `DataBaseProcessor` 进入 `ServiceManager.sendmessage`；回包按命令和序号关联 | 复用 Fly 已建立的进程内通信环境，该 Wire 路径没有另建 socket |
| 备份恢复 | `.dhp` 保存参数；按名称匹配当前设备元数据并筛选类型/范围/歧义；失败时停止后续恢复 | 可以借鉴预览和兼容性检查，但前面已成功的修改不会自动回滚 |

以上是代码路径，不是本次设备结果。E2 路径不等于 SDK 本地缓存，但也没有证明某个参数控制标准 RID。它不推翻既有 RID 参数缺失或外部 Binder 失败记录。`Wire.cancel()` 与本地等待结束不证明请求已完全静止。

还有几处应重写：可写属性被固定为 `1`，不能当作设备授予的权限；“完整”仅覆盖本次发现并接受的行；备份可能把旧参数值配上导出时的新身份；页面任务代次并非连接会话锁。电机/飞行状态只是写前顺序读取，批量恢复也未持续绑定同一飞机。超时、失败码和异常被合并为 null，写成功但读回失败时缺少持久的“结果未知”记录。

## 为什么不能只复制几个类（C-482）

Manifest 直接使用 `DJIApplication`。所查 `UAVApplication` 初始化 MultiDex、ApplicationLike 和应用服务；`UAVSDKManager` 初始化 native SDK、数据连接及回调环境。`JNIKeyValue` 的 GET/SET 最终进入 `sdk_jni`。这些是实际的宿主依赖，复制 UI 或 Java wrapper 不会自动获得另一个进程里的连接与状态。

安装器还固定检查 `dji.go.v6` 的签名证书、共存版本标记及安装后 APK 摘要。修改后重签不能假定原向导仍会接受；Android 的同包更新也检查签名。因此需要独立设计自己的包身份、安装和后续更新流程，不能借用作者的签名身份。[Android 签名说明](https://developer.android.com/studio/publish/app-signing#considerations)

| 开发方式 | 判断 |
| --- | --- |
| 自己维护源码模块和少量版本适配，使用固定 APK 作本地基底 | 推荐。把 UI、状态机、日志和验证逻辑留在可维护源码中；复用宿主连接的接入仍需实际构建验证 |
| 直接对 RedFly APK 做小范围二进制修改 | 可用于限定实验，但必须记录每个改动、基底摘要和签名/安装边界；升级时重新验证 |
| 将整个 Fly 反编译成 Java 后全面重建 | 当前不选。缺少原始工程及完整依赖，反编译也已有错误还原；会把工作扩大到无关的大量代码 |

## 下一步工程范围

第一项应是一个可重复构建的进程内诊断模块：识别固定宿主版本、等待原连接就绪、读取已知状态，并区分缓存、实际请求、回调和新回读。只读阶段用于证明接入和状态来源，最终目标仍是实际 RID 控制面板及各字段的独立验收。

确认接入后，再为一个已识别的控制实现完整的原值记录、一次变化、独立回读、恢复及恢复读回。状态机和失败日志应由自研模块统一管理，不继承 RID Kill 的无限循环、默认开启或无原值恢复行为；参数编辑器的部分恢复成功也不能冒充事务完成。

最后单独处理应用的安装/更新和重连/重启结果。基于 APK 的修改只在本地固定输入上生成，仓库保留自研源码、适配说明、工具和测试；厂商 APK/DEX/SO 与反编译源码继续排除。当前没有目标设备，尚无模块运行、飞机接受或标准 RID RF 的新增结果。
